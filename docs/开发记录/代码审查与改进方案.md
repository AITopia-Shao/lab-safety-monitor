# 实验室安全事前干预监测系统：代码审查与改进方案

> 审查范围：`labguard` 下的全部 Python 源码、两个 `.spec`、`requirements.txt` 和 `environment.yml`，并解析了 `models/*.pt` 里的类别表。
> 严重程度分三级：**🔴 致命**（安全功能失效，或演示时一眼就能看出问题）、**🟠 严重**（功能错误或有隐患）、**🟡 一般**（代码质量、体验和可维护性）。

---

## 任务一：Bug 与漏洞清单

### 先说最关键的发现：代码和模型对不上

我从两个模型文件里读出了真实的类别表：

| 模型 | 实际类别 |
|---|---|
| `ppe_best.pt`（YOLO11n） | Drinking, Eating, Gloves, Googles, Head Mask, Lab Coat, Mask, No Gloves, No Head Mask, No Lab coat, No Mask, No googles |
| `chem_best.pt`（YOLO11n） | Beaker, Burette, Conical Flask, Flat Bottom Flask, Funnel, Measuring Cylinder, Pear shaped flask, Pipette, Reagent Bottle, Round Bottom Flask, Test tube, Titrarion, Volumetric flask, Wash Bottle |

由此引出下面三个致命问题。

#### 🔴 1. PPE 模型没有 "Person" 类，"无人值守"判断基本是错的
- 位置：`LabSafetyMonitor/dual_inference.py:463`
- 代码只有在识别到 `["Person","Head","Mask","No Mask","Eating","Drinking"]` 之一时才认为"有人"。但模型里根本没有 Person 和 Head 这两类。
- 后果：一个人穿着实验服、戴着护目镜和手套站在画面里，只要没识别出口罩相关的框，就会被判成"没人"，5 秒后报**无人值守**。反过来，人走了但留下一件实验服挂在椅子上，系统还可能认为有人在。
- 这个结果又是"干烧断电"的必要条件，所以整条断电链路的输入一开始就不可靠。

#### 🔴 2. 物品模型里没有任何加热设备，"加热设备检测"实际上等于"看到了玻璃器皿"
- 位置：`src/core/state_machine.py` 里的 `DEFAULT_HEATING_KEYWORDS`
- 关键词里的 burner、alcohol_lamp、hotplate 在模型中都不存在。能匹配上的只有 beaker、flask、test tube、titrarion，全是普通玻璃器皿。
- 更糟的是，`Volumetric flask`（容量瓶）也会匹配到 "flask"，被当成加热设备。容量瓶在规范里恰恰是**禁止加热**的。评委懂化学的话，一眼就能看出来。

#### 🔴 3. 用"室温 > 55℃"判断干烧，物理上说不通
- 位置：`state_machine.py` 里的 `HIGH_TEMP_THRESHOLD = 55.0`，传感器是测环境温湿度的。
- 真实干烧时，烧杯底部可能已经几百摄氏度，房间温度却几乎不变。等室温到 55℃，实验室多半已经着火了。所以现在这条规则只能靠 `env_controller.py` 手动拖滑块来触发，在真实场景里永远不会生效。

#### 🔴 4. 断电指令没发出去，界面也显示"已断电"
- `serial_comm.py:42`：串口没连上时，`send_power_off()` 直接 `return`，不抛异常也不返回状态。
- `state_machine.py:170`：调用完就打印"成功下发断电帧！"，告警文本也写"系统已执行硬件闭环"。
- 加上下一条的串口号问题，在 Windows 上**每一次断电都是假的，但界面会说成功**。对安全系统来说，这是最危险的一类 bug：它不是失败，而是"假装成功"。
- 另外，协议没有 ACK（下位机确认）和继电器状态回读，上位机无法知道继电器到底动作了没有。

#### 🔴 5. 串口号写死成 Linux 路径，两个模块还在抢同一个口
- 涉及位置：`main_window.py:470`、`main_window.py:671`、`serial_comm.py:10`，全部是 `/dev/ttyUSB0`。
- 在 Windows 上永远打不开，传感器始终处于模拟模式，断电指令也永远发不出去。
- 在 Linux 上接真机时，`SensorWorker`（9600 波特率）和 `SerialComm`（115200 波特率）会同时打开**同一个设备**，波特率还不一样，两边读到的都会是乱码。

#### 🔴 6. 只有温湿度告警会进日志，而且马上被覆盖；视觉告警只停留在画框上
- `main_window.py:1120`：`update_display` 每一帧都用 `setText(log_str)` 把终端整个替换掉。`on_safety_alert` 追加的告警日志，约 30 毫秒后就被冲掉了。
- `dual_inference` 已经算出了 `ppe_violation`、`eating_drinking`、`sleeping`、`falling_warning` 和 `violations` 列表，但 UI **一个都没有用**：不记日志、不自动抓拍、不发声光提示。界面上能看到的只有画面里的红框。
- 文档写的"AI 捕捉到危险自动生成报警卡片"并没有实现，卡片只能手动点"抓拍"生成。

### 🟠 严重问题

| # | 位置 | 问题 | 后果 |
|---|---|---|---|
| 7 | `dual_inference.py:466` 和 `:526` | 用固定的 `self.height`（480）去判断位置，但视频或摄像头的实际分辨率可能是 720p 或 1080p，而且摄像头不一定接受 `set()` 设置的尺寸 | 1080p 视频下，"睡觉"和"高处物品"的判断区域完全错位 |
| 8 | 同上 | "睡觉"的判据是任意一个 PPE 框的中心落在画面下方 40%；"高处坠落"的判据是容器中心落在画面上方 30% | 跟机位强相关：摄像头装高一点，人人都在"睡觉"；俯拍桌面时，桌子后半部分的烧杯都会被判成"高处"。这也不是"坠落"的语义，坠落风险应该看容器离桌边多近 |
| 9 | `dual_inference.py:451` 和 `:491` | 关闭人员模型，或画面是黑屏（单桌面模式）时，永远找不到人，5 秒后必然判成"无人值守" | 关掉一个模型，就可能误触发干烧断电链路 |
| 10 | `dual_inference.py:161` 和 `:416` | 队列满了就**丢弃新帧**，保留旧帧 | CPU 推理慢的时候，画面和告警会滞后好几帧，安全系统的实时性变差。应该丢掉最旧的帧 |
| 11 | `dual_inference.py` 的 `open_source` 和重试逻辑 | 没有摄像头时，每 3 秒扫描 6 个索引 × 3 种后端，每次都要真实 `read()` 一帧 | 生产者线程会卡住好几秒，仿真画面一卡一卡的；重试时也没有释放之前的 cap |
| 12 | `dual_inference.py:18` | 没装 ultralytics 时**静默**换成 MockYOLO，什么都检测不到，只在控制台打印一行 | 安全系统在"失明"状态下照常运行，界面看起来一切正常。安全系统出故障时应该进入报警或降级状态，而不是悄悄继续 |
| 13 | `serial_comm.py:62` 和 `:64` | ① 每次固定读 8 字节，没有帧同步：丢掉 1 个字节之后，之后的每一帧都会错位，再也对不齐 ② 接收线程没有 try/except，拔掉 USB 后线程会静默退出 ③ `disconnect()` 先关串口，接收线程接着访问 `in_waiting` 就会抛异常 | 下位机通信不可靠 |
| 14 | `state_machine.py` 的 `evaluate` | 没有时间维度的防抖：某一帧漏检烧杯，状态就从 CRITICAL 跳回 NORMAL；断电后也不锁定 | 断电后 UI 显示"SAFE / 继电器供电常通"，而继电器其实已经断开，状态前后矛盾 |
| 15 | `main_window.py:1313` | "自定义模型"按钮只弹窗说"成功挂载"，实际上什么都没做 | 功能是假的，评委点一下就会发现 |
| 16 | `main_window.py:369` | 遥测卡片自己又判断一遍 `temp > 55`，和状态机不一致 | 状态机是 NORMAL，卡片却显示 ALERT |
| 17 | `sensor_worker.py` | 串口失败一次后就永远停在模拟模式，不再重连；docstring 里说的"动态校验码过滤毛刺"也没有实现；没有数据超时检测（传感器不再发数据时，界面一直显示最后一个值） | 硬件热插拔之后无法恢复；数据卡住的值看起来跟正常值一样 |
| 18 | `src/bootstrap.py:59` 和 `:63` | 把别的 venv 或 conda 环境（比如 Python 3.10 的 `lab_safety`）的 site-packages **插到 sys.path 最前面**。你本机的 Python 是 3.13 | 很可能出现 `DLL load failed` 或 numpy、torch 的 ABI 冲突，而且很难排查。直接用对应环境的 Python 运行就行，不应该靠这种方式 |
| 19 | `requirements.txt` | `numpy<2.0` 没有 Python 3.13 的安装包；写的是 PyQt6，代码却优先用 PySide6；`.spec` 里打包的也是 PyQt6 | 在你现在的 Python 3.13 上 `pip install` 会失败；两个 Qt 绑定都装上时，打包体积会翻倍，还可能冲突 |

### 🔒 安全漏洞（威胁面不大，答辩时可能被问到）

| # | 问题 | 说明与建议 |
|---|---|---|
| S1 | **IPC 遥测文件可被伪造** | 只要串口不可用，主程序就会信任 `%TEMP%/lab_safety_env_telemetry.json` 里的温湿度。本机任何进程都能写这个文件，既可以伪造高温触发断电，也可以一直写 25℃ 来**压住真实告警**。正式版应该删掉这个通道，或者只在 `--demo` 参数下启用，并加签名或随机 token |
| S2 | 环境变量 `CUSTOM_CAMERA_MODULE_PATH` 可以注入任意 Python 模块 | 能改环境变量的人就能在主程序里执行代码。正式版建议删掉，或改用白名单配置 |
| S3 | 手机摄像头使用明文 HTTP，且没有鉴权 | 同一局域网内谁都能看到实验室画面。至少要在 IP Webcam 里开启用户名和密码，并提示用户这一点 |
| S4 | `.pt` 模型本质上是 pickle 文件 | 如果以后把"自定义模型"功能真正做出来，加载陌生的 `.pt` 文件就等于执行任意代码。应该只允许加载自己训练的模型，或者改用 ONNX |
| S5 | 安全闭环完全依赖上位机 | PC 死机、软件崩溃或 USB 被拔掉时，加热器会**一直通电**，没有任何兜底。这是架构层面的漏洞，见任务二的方案 |

### 🟡 一般问题
- `camera_manager.py` 和 `inference_logic.py` 是死代码，没有被引用，`.spec` 却还在 hiddenimports 里引用它们。
- 55℃ 和 80% 这两个阈值在 3 个文件里各写了一遍；所有参数都是硬编码，没有配置文件。
- 每个文件开头都复制了一段 venv 注入代码。
- `InferenceThread.__init__` 在主线程里加载 YOLO 模型，启动时界面会卡住好几秒。
- 置信度允许设成 0.00，这时画面会被检测框淹没。
- "正确 +1.75 分"的计分方式可以随手刷：手动抓拍 20 张，全部点"正确"就是满分。这对系统效果没有任何证明力。
- 没有事件持久化（文件或数据库），程序一关，所有记录都没了。

## 任务二：逻辑与功能的不足，以及更好的方案

### 2.1 现在的根本问题（不是个别 bug，而是设计层面的）

1. **"事前干预"没有体现出来。** 现在的流程是"检测，然后画框"，最多再加一个断电。真正的"事前干预"应该是**分级的**：先提醒（声光、语音），再通知管理员，最后才是强制断电。现在中间两级是空的。
2. **视觉判断都是单帧、靠位置的启发式规则**，没有时间平滑，没有人员追踪，也没有场景标定。所以换个机位、换个人，结果就不一样，误报和漏报都很多。
3. **模型能力和业务规则脱节。** 规则里需要人、加热设备、桌边，模型都给不了；模型能给的口罩、手套、护目镜、实验服，规则里又没用上。
4. **传感器选错了物理量。** 干烧应该测**容器或热源的表面温度**，可以用红外测温或热电偶，而不是室温。
5. **安全闭环放在了最不可靠的地方**，也就是 Windows 上的 Python GUI 进程里。
6. **双摄的"协同"偏弱。** 现在两路画面是各算各的，只在状态机里做了一个 AND。真正的协同应该是：全景负责"人在不在、穿戴是否合规、人在干什么"，桌面负责"台面上有什么、离边缘多远、是否在加热"，两者的结果按**同一个工位**关联起来。
7. **缺少可以拿来证明效果的数据。** 没有事件库，没有准确率和召回率，也没有响应时间统计。比赛答辩最需要的恰恰是这些数字。

### 2.2 目标架构

```
┌──────────────────────── 上位机 PC（Python）──────────────────────────┐
│                                                                       │
│  CamA 全景 ─┐                                                         │
│             ├─► 采集层（每路独立线程，丢旧帧，记录时间戳）             │
│  CamB 桌面 ─┘          │                                              │
│                        ▼                                              │
│        感知层：                                                        │
│          · 全景：person 检测 + ByteTrack 追踪 + PPE 检测 + 姿态(pose)  │
│          · 桌面：器皿 / 热源检测 + 台面 ROI 与桌边线标定               │
│                        │  输出"结构化观测"（每帧、每个人、每件物品）    │
│                        ▼                                              │
│        规则层（每条规则一个有限状态机）：                               │
│          IDLE → SUSPECT（N 秒内 M 帧命中）→ CONFIRMED → ACK → RESOLVED │
│                        │  输出"事件"（类型、等级、截图、短视频片段）    │
│                        ▼                                              │
│        处置层（分级干预）：                                             │
│          L1 声光 + 语音提醒 → L2 企业微信/钉钉通知管理员 → L3 断电     │
│                        │                                              │
│        存储层：SQLite 事件库 + 截图 / 片段，评审结果写回数据库         │
│        展示层：PySide6 界面（只负责显示，不做业务判断）                 │
│                        │                                              │
│        SerialManager（唯一的串口所有者：自动识别端口、帧同步、        │
│                       CRC、ACK、心跳）                                 │
└────────────────────────┼──────────────────────────────────────────────┘
                         │ USB 串口，带心跳
┌────────────────────────┼──── 下位机 MCU（固件独立兜底）─────────────────┐
│  传感器：SHT30 温湿度 · MLX90614 红外测温 · MQ-2 烟雾/可燃气             │
│  执行器：继电器 · 蜂鸣器 · 三色灯 · 语音模块 · 物理复位按钮               │
│  本地硬规则：红外温度 > 硬上限 或 烟雾超标 → 立刻断电（不依赖 PC）        │
│  看门狗：超过 5 秒没收到 PC 心跳 → 亮黄灯；正在加热且失联超过 30 秒 → 断电│
│  断电后锁定：只有按物理复位键才能恢复供电                                 │
└───────────────────────────────────────────────────────────────────────┘
```

**核心原则：PC 负责"聪明"，MCU 负责"可靠"。** 视觉 AI 用来做早期预警和分级干预；真正的断电兜底由 MCU 独立完成，PC 挂了也照样生效。这一点在答辩时也很有说服力。

### 2.3 逐项改进方案

#### A. 视觉感知层
| 项目 | 现状 | 改进方案 |
|---|---|---|
| 人员检测 | 用口罩类间接判断 | 增加 **COCO 预训练的 yolo11n**，只保留 person 类（不用训练，直接可用）；也可以在 PPE 数据集里补标 person 类后重新训练 |
| 人员与 PPE 的对应 | 没有 | 用 `model.track(persist=True)`（ByteTrack）给每个人分配 ID，把 PPE 框按"框中心落在哪个人的框内"归属到对应的人，按人统计违规 |
| 违规判定 | 单帧有框就报 | **时间投票**：同一个人在最近 3 秒内超过 70% 的帧命中 "No googles"，才确认违规。误报会大幅下降 |
| 饮食检测 | 依赖 Eating 类 | 保留 Eating/Drinking 类，再加上 pose 判断"手腕关键点靠近嘴部"做交叉验证 |
| 睡觉/伏案 | 框的 y 坐标 | 用 **yolo11n-pose**：头部关键点低于肩部、持续 N 秒、并且躯干基本不动，才判定 |
| 无人值守 | 5 秒没有口罩类 | person 追踪 ID 全部消失超过 T 秒（可配置，建议 30 到 60 秒），**同时**桌面上有正在进行的实验（有热源或红外温度偏高），才算真正的"无人值守实验" |
| 加热设备 | 用器皿冒充 | 方案一：在 chem 数据集里补标酒精灯、电热板、加热套后重新训练；方案二（更推荐）：**用红外测温来判断"是否在加热"**，比视觉可靠得多 |
| 坠落风险 | 画面上方 30% | 首次部署时在桌面画面上**画出台面多边形和桌边线**，存进配置文件；容器底部中心到桌边线的距离小于阈值（比如 3 厘米，可以用单应变换换算成真实距离）就预警 |
| 分辨率 | 写死 480 | 所有坐标先归一化到 0 到 1，再做判断 |
| 双摄关联 | 只有 AND | 把"工位"作为关联单位：全景画面里划出工位区域，桌面摄像头对应同一个工位，事件里同时记录"谁"和"在做什么" |

#### B. 规则与事件层（替换现在的 `SafetyStateMachine`）
- 每种事件类型配置一组参数：`触发条件、防抖时间、冷却时间、等级、处置动作`。全部写在 `config.yaml` 里，不用改代码。
- 建议的事件类型和对应的干预方式：

| 事件 | 判定 | 干预等级 |
|---|---|---|
| 未穿实验服、未戴护目镜、未戴手套 | 追踪 + 时间投票 | L1：语音"请佩戴护目镜"，亮黄灯 |
| 实验区饮食 | 类别 + pose | L1，持续 10 秒仍未停止则升到 L2 |
| 伏案睡觉 | pose + 持续时间 | L1，持续时间更长则升到 L2 |
| 容器靠近桌边 | ROI 距离 | L1 |
| 加热时人员离开 | 加热中 + 无人超过 T 秒 | L2 通知；超过 2T 秒升到 L3 断电 |
| 干烧 | 红外温度超过 110℃ 或升温速率超过阈值 | **L3 立即断电**（MCU 本地也会执行） |
| 烟雾或可燃气体 | MQ-2 读数超过阈值 | L3 断电，声光报警，通知管理员 |
| 高湿 | 湿度超过 80% | L1 提示 |
| 系统自身故障（模型未加载、摄像头掉线、MCU 失联） | 健康检查 | L2，并在界面上用醒目的红色横幅提示 |

- **断电锁定**：L3 触发后进入 `LOCKED` 状态，界面持续显示"已断电，等待人工复位"，并以 MCU 回传的继电器状态为准。
- 干烧阈值的物理依据：水在常压下最高约 100℃。只要容器里还有水，外壁温度就不会明显超过 100℃；一旦超过 110 到 120℃，基本可以判断已经烧干。另外，**升温速率 dT/dt 的突然增大**是更早的信号。

#### C. 通信协议（替换现在的 5 字节帧）
```
帧格式: AA 55 | LEN | SEQ | CMD | PAYLOAD... | CRC16 | 0D
上行: 0x10 遥测（温度、湿度、红外温度、烟雾、继电器状态、本地告警位）, 周期 500ms
      0x11 ACK(seq)
      0x12 本地事件（MCU 自主断电、复位键被按下）
下行: 0x01 心跳(每 1s)  0x02 断电  0x03 声光等级  0x04 播放语音(n)  0x05 请求状态
```
- 用状态机逐字节解析，遇到包头 `AA 55` 就重新同步，这样能解决现在帧一旦错位就再也对不齐的问题。
- 断电指令要等到 ACK，并且回读到继电器状态，才在界面上显示"已断电"；200ms 内没收到 ACK 就重发，连续 3 次失败就报"执行器故障"。
- 端口用 `serial.tools.list_ports` 按 VID/PID 自动识别（CH340 是 1A86:7523，ESP32-S3 原生 USB 是 303A:xxxx），不再写死。
- **只用一个串口、一个所有者**：温湿度不再走单独的口，统一放进遥测帧里。

#### D. 工程化
- 只用一个 Qt 绑定（建议 **PySide6**）。删掉 bootstrap 里注入 sys.path 的做法，改用 `conda activate lab_safety` 或项目自己的 `.venv`。
- `config.yaml` 统一管理：摄像头源、串口、阈值、ROI、通知用的 webhook。
- 模型加载失败时**不要用 Mock**。界面应该显示红色横幅"视觉模块离线"，同时上报 L2。演示模式用 `--demo` 参数单独开启（同时开启 IPC 模拟通道）。
- 事件写进 SQLite（时间、类型、等级、人员 ID、截图路径、前后各 5 秒的视频片段、处置结果、评审结论）。
- 评审面板：事件**自动**进入列表，评委点"正确/误报"后写回数据库，界面实时显示 **Precision（准确率）、各类事件数量、平均响应时间（从违规出现到语音提醒的秒数）**。可以保留 35 分的计分作为展示，但最好由真实数据算出来。
- 一键导出评测报告（CSV 加 HTML），里面放混淆统计和典型截图。
- 拆分目录：`capture/`、`perception/`、`rules/`、`actuation/`、`storage/`、`ui/`，每层只通过数据结构通信，方便写单元测试（比如录一段视频来回放测试规则）。

### 2.4 建议的开发顺序

1. **第 1 周**：清理工程（统一 Qt 绑定、加配置文件、删死代码、修队列和串口），重写 SerialManager 和新协议，同时把 MCU 固件写好（传感器读取、本地硬规则、看门狗）。**先把硬件闭环做扎实。**
2. **第 2 周**：感知层加入 person 检测、追踪和 pose，PPE 按人归属，加入时间投票；桌面摄像头加入 ROI 标定工具。
3. **第 3 周**：事件规则引擎、分级干预、SQLite、自动抓拍和片段保存、评审面板和指标统计。
4. **第 4 周**：录 10 到 20 段场景视频做回放测试，调阈值，统计准确率、召回率和响应时间，整理成答辩材料；准备演示道具。

### 3.3 接线示意（以 ESP32-S3 为例）

```
ESP32-S3                      外设
───────────────────────────────────────────────
3V3 / GND  ─────────────────  所有 I2C 模块的电源
GPIO8 (SDA) ─┬──────────────  SHT30 SDA
             ├──────────────  MLX90614 SDA
             └──────────────  OLED SDA
GPIO9 (SCL) ─┴─ 同上 SCL      (三个 I2C 地址不同: 0x44 / 0x5A / 0x3C)
GPIO1 (ADC) ────────────────  MQ-2 AO （MQ-2 用 5V 供电，AO 要分压到 3.3V 以下）
GPIO10 ─────────────────────  继电器 IN（低电平触发的模块注意逻辑反转）
GPIO11 ─────────────────────  警示灯 红 （通过 MOSFET 或三极管驱动）
GPIO12 ─────────────────────  警示灯 黄
GPIO13 ─────────────────────  警示灯 绿 / 蜂鸣器
GPIO17 (TX) / GPIO18 (RX) ──  DFPlayer RX / TX（DFPlayer 的 RX 串 1kΩ 电阻）
GPIO4 ──────────────────────  复位按钮（内部上拉，按下接地）
USB (原生) ─────────────────  PC：USB-CDC 串口，同时给 MCU 供电

继电器触点（常开 NO）─ 串入 12V 加热片回路（演示用）
                     └ 或通过成品控制插座盒控制 220V 加热板（实际部署）
```

**继电器一定要接"常开（NO）"触点，并且上电默认断开**：MCU 启动或复位时，加热器不应该自动通电，需要 PC 上线、自检通过后才闭合。这就是"失效安全（fail-safe）"的设计。

### 3.4 MCU 固件逻辑（伪代码）

```c
loop every 100ms:
    读取 SHT30 / MLX90614 / MQ-2（每 500ms 一次）
    解析 PC 下发的帧 → 处理 心跳/断电/声光/语音 指令 → 回 ACK

    // ① 本地硬规则：不依赖 PC
    if (ir_temp > HARD_LIMIT_C(如 150) || ir_dTdt > RATE_LIMIT || smoke > SMOKE_LIMIT)
        relay_off(); latched = true; light(RED); buzzer(ON); report(0x12, reason);

    // ② 看门狗
    if (now - last_heartbeat > 5s)      light(YELLOW_BLINK);   // PC 失联提示
    if (now - last_heartbeat > 30s && relay_is_on && ir_temp > 60)
        relay_off(); latched = true;                           // 失联 + 正在加热 → 兜底断电

    // ③ 锁定与复位
    if (latched && reset_button_pressed_for(2s))
        latched = false; light(GREEN);   // 只有人到现场按下按钮才能解除锁定
    if (!latched && pc_requests_power_on && selftest_ok) relay_on();

    每 500ms 上报遥测帧 0x10（包含 relay 实际状态与 latched 标志）
```

### 3.5 物理部署建议
- **全景摄像头**：装在实验台斜上方 2 到 2.5 米处，倾斜 30 到 45 度，保证能看清人的上半身和面部。逆光（背对窗户）会严重影响护目镜和口罩的识别。
- **桌面摄像头**：用万向臂在台面正上方 50 到 70 厘米处俯拍，画面里要能看到**完整的台面和靠近人的那条桌边**，方便标定 ROI。
- **红外测温**：MLX90614 的视场角约 90°（BAA 型号），测量的是视场内的平均温度。要对准加热板或烧杯底部，距离 **2 到 5 厘米**。想测得更准，可以选窄视场的 **MLX90614ESF-DCI（5°）**，价格约贵 40 元。
- **MQ-2**：装在加热位上方约 30 厘米处。上电后需要预热 1 到 2 分钟，首次使用需要老化 24 到 48 小时。
- **控制盒**：MCU、继电器和电源都装进 ABS 盒，**强电和弱电分开走线**。涉及 220V 的部分只用成品插座盒，或者请有电工资质的人接线。比赛演示时**优先用 12V 加热片**，评委看着更安心，你也没有安全风险。

### 3.6 演示脚本建议（答辩用）
1. 正常穿戴后进入：绿灯亮，界面显示"合规"。
2. 摘下护目镜：约 3 秒后语音提示"请佩戴护目镜"，亮黄灯，自动生成事件卡片。
3. 把烧杯推到桌边：触发坠落风险提醒。
4. 打开 12V 加热片加热少量水，然后人离开：先触发 L2，企业微信群收到通知（附截图）。
5. 水烧干，红外温度快速上升：**MCU 本地断电**，红灯和蜂鸣器报警，界面显示"已断电（已收到 ACK），等待人工复位"。
6. **拔掉 PC 的 USB 线**，再演示一次：即使上位机失联，MCU 仍然能独立断电。这是全场最有说服力的一步。
7. 最后展示评审面板：本次演示的事件数量、Precision 和平均响应时间。
